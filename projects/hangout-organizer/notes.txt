WHAT THE APP DOES NOW (all built this session, on top of the original build):

  Polls, not sessions. A poll owns the window + share token; sessions hang off it as the things
  being booked, each with its own quorum rule, ALL scored against one set of answers. Badminton and
  pickleball over the same dates = one link, one grid. Adding an activity to a running poll needs
  nobody to re-answer.

  Per-activity opt-in. A poll with >1 activity asks friends "which of these are you up for?".
  Stored as opt-OUTS (absence = in) to preserve the no-re-answer property. The host page names
  anyone who opted out, and separately names anyone who answered BEFORE an activity was added —
  they are being counted without having said yes.

  Roster groups. Poll addressed to everyone / a group / hand-picked. Resolved list FROZEN onto the
  poll at creation, same rule as sport thresholds being copied.

  Date-only polls. "Which dates suit the trip?" — modelled as a poll whose slot is one whole day,
  so the quorum engine is untouched. sport_id is nullable for these.

  Grouped bookable windows. A 3-hour free stretch was showing as five near-identical rows; now one
  block with the start times inside it, drawn as bars on a per-day timeline. Merging stops where
  the sustained headcount would drop.

  Clash warning between two confirmed sessions in the same poll that share people.

  WhatsApp: editable message preview, an "Open in WhatsApp" wa.me deep link, URL alone on the last
  line so WhatsApp linkifies it, and a warning while SITE_URL is still localhost.

  Overnight windows (22:00–00:00, 21:00–01:00). Grid headers carry the month; row labels are slot
  ranges. Slots default to 60 minutes, or 30.

FUTURE ENHANCEMENTS (captured 2026-09-09, not started)
================================================================================

1. PERFORMANCE — "the response is not smooth"

   MEASURE BEFORE CHANGING ANYTHING. The likely causes are in this order, and
   only the first two are worth guessing at:

   a) REGION MISMATCH. Check the Supabase project's region against the Vercel
      function region. If Supabase is in Singapore and the function runs in
      Washington, every single query pays ~200ms each way, and the poll page
      makes a lot of them. This is by far the most likely dominant factor and
      the cheapest to fix — set the Vercel function region to match Supabase.
   b) SERIAL ROUND TRIPS on the poll page. It is 13 Supabase calls, and four
      are awaited OUTSIDE the Promise.all (page.tsx lines 48, 74, 94, 145):
      poll -> invitees -> people -> opt-outs -> attendees, each waiting on the
      one before. The invitee/people pair could be one join; opt-outs and
      attendees could join the Promise.all once the session ids are known.
      Look at collapsing these into a Postgres view or an RPC.
   c) NO CACHING AT ALL. 11 pages are pinned `export const dynamic =
      "force-dynamic"`. That was right while the model was changing under us,
      but /venues, /people and /templates barely change and could revalidate
      on a tag instead.
   d) Vercel free-tier cold starts, and Supabase free-tier auto-pause after
      ~a week idle. Neither is fixable on a free plan; just know they exist
      before blaming the code.

   NOTE: the sluggishness seen during development was mostly `next dev`
   compiling routes on demand. That does NOT apply to the deployed build, so
   measure on production, not localhost.

2. MOBILE UI/UX

   The FRIEND-facing side is already touch-first (drag grid with touch-action
   none and elementFromPoint tracking, big tap targets on the date grid). The
   HOST side is the weak part and was built desktop-first:
     - the poll page is very long and scrolls a lot on a phone
     - the heatmap is a wide table that overflows horizontally
     - BookableBlocks' timeline bars are narrow on a small screen
     - the new-poll form is a 2-column grid that gets cramped
   Start with the poll page, since that is the one used while standing in a
   court car park deciding what to book.

3. ROSTER SECTION

   Currently just a flat list of names with active/inactive. Wanted:
     - total count, and active vs inactive split
     - which groups each person belongs to, shown on their row
     - probably: filter by group, and a count per group (the group cards
       already show a count, the people rows do not show membership)
   All of this is available from roster_group_members, which /people already
   loads - it is presentation, not new queries.

2026-09-21 — POLLS BECAME PER-DATE WINDOWS (migration 013)
================================================================================

WHAT CHANGED
  A poll used to be a rectangle: poll_start_date..poll_end_date crossed with ONE
  day_start_time..day_end_time. Now the host picks dates individually on a
  calendar and gives each date its own windows, and a date can carry several.

  New table poll_windows(poll_id, day_date, start_time, end_time). Both times
  NULL = a whole date (trip polls). polls.day_start_time/day_end_time dropped.

  poll_start_date/poll_end_date SURVIVE but only as derived sort bounds —
  polls_status_idx and the dashboard ordering are built on them. The polled set
  is poll_windows. Never render "when is this poll" from the bounds.

NEW / CHANGED FILES
  migrations/013_per_date_windows.sql   truncates poll data, creates poll_windows
  src/lib/poll-windows.ts   NEW, pure: parseWindows / longestRun / validateWindows
