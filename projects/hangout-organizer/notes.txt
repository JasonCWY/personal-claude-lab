This session was a review of the deployed-app surface. Three things changed.

1. RLS was scoped to the host, and this was a real hole, not a tidy-up.
   The old policy was `for all to authenticated using (true)`. The anon key and the project URL
   both ship in the browser bundle, so a stranger can POST to Supabase's own auth endpoint, get a
   magic link for their OWN address, and hold a valid `authenticated` JWT without ever loading
   this app. From there PostgREST would have handed them every table. The app-side gates
   (auth/callback signing non-hosts out, the (host) layout re-check) never see that request.
   The migration now creates a `host_allowlist` table (RLS on, zero policies, so nothing but
   service_role can read it) and an `is_host()` SECURITY DEFINER function with a pinned
   search_path; every policy is `using (is_host())`.
   => You must replace `you@example.com` near the bottom of the migration with your real address
      before running it. It has to match HOST_EMAIL. Leave the placeholder and every page is empty.

2. Open redirect in auth/callback/route.ts. `next` comes back from the magic link, and
   `next.startsWith("/")` also passes `//evil.com`, which browsers read as protocol-relative.
   Now rejects a second leading slash or backslash.

3. Input caps on api/public/s/[token]/availability. That endpoint is open to anyone with the
   link; `comment` was unbounded. Now MAX_SLOTS 2000, MAX_COMMENT 500.

Deliberately NOT changed: `shouldCreateUser` on the login form stays true. Setting it false is
security theatre — an attacker never uses our client. The real control is the Supabase dashboard
toggle, which is now step 4 of the README.
